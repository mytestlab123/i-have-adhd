How this page is organized

Source labels refer to repository content. Illustration labels are newly written examples, not real system results. Amit adaptation labels are proposals based on your preferences, not claims about what upstream already implements.

Use Listen for a short spoken explanation of the current section. It requires a local voice exposed by your browser. Nothing plays automatically. Source links open GitHub only when clicked.

The author's rationale, not a clinical assessment

The skill motivates its rules through working-memory load, starting friction, time estimation, and visible progress. These are the author's framing. This guide does not treat the repository's simplified ADHD statements as clinical evidence or universal descriptions of people with ADHD.

You can use the response patterns because they help your workflow, without making any medical claim.

02 / LEARN THE PATTERN

Ten rules. One card at a time.

The rule names follow the source. Examples and personal adaptations are clearly labeled.

01
CANONICAL RULE

Lead with the next action

Put the useful part first.

Your reader should not have to dig through an introduction to find the answer or the next action.

BEFORE / ILLUSTRATION

There are several things to consider about the failed job. Let us first examine the wider environment.

AFTER / ILLUSTRATION

The job failed at authentication. Next: inspect the failed request before changing anything.

Why this rule matters

The canonical rule puts the command, path, snippet, or action before context. In this learning page, examples are illustrative, not instructions to change a real system.

Amit adaptation

Lead with the result on status questions, and the next action on task questions. Do not generate commands unless requested.

Proposed personal preference. This page does not edit or activate the upstream skill.

02
CANONICAL RULE

Number multi-step tasks

One step. One bounded action.

Use the fewest steps that preserve the actual task. Separate actions that need separate decisions.

BEFORE / ILLUSTRATION

Check the report, inspect the instance, decide what to do, and then update the runbook and review everything.

AFTER / ILLUSTRATION

1. Read the failing check. 2. Verify the affected resource. 3. Propose one bounded repair.

Why this rule matters

The source asks for numbered steps when work has more than one step. It warns against packing multiple sequences into a single numbered item. A short plan is useful only when it remains complete.

Amit adaptation

Show the immediate working set, not every possible future task. Let the agent do work it is authorized and equipped to perform.

Proposed personal preference; not an upstream modification.

03
CANONICAL RULE

End with one concrete next action

Leave one obvious place to start.

When something remains open, finish with one specific next action rather than a menu of follow-ups.

BEFORE / ILLUSTRATION

Let me know whether you would like a review, another test, a diagram, or a deeper explanation.

AFTER / ILLUSTRATION

Next: review the one changed file.

Why this rule matters

The canonical rule suggests a next action the reader can begin in under two minutes. That is a starting-point heuristic, not a claim that the entire task will finish in two minutes.

Amit adaptation

End execution and workflow responses with exactly one Next. Do not invent extra work after a simple factual answer.

Proposed personal preference; not an upstream modification.

04
CANONICAL RULE

Suppress tangents

Finish this issue first.

Keep unrelated improvements out of the current task. A necessary clarification is not a tangent.

BEFORE / ILLUSTRATION

The test passes. Also, we could redesign logging, update the theme, and migrate the deployment.

AFTER / ILLUSTRATION

The test passes. No additional changes are needed for this task.

Why this rule matters

The source says to finish the first issue before raising another. It also says the agent should answer questions that arise during its own work where possible, rather than handing avoidable work back to the reader.

Amit adaptation

Park ideas without turning them into extra branches, issues, or new missions. Ask about a follow-up only when it is useful.

Proposed personal preference; not an upstream modification.

05
CANONICAL RULE

Restate state every turn

Show where we are, not all we did.

A compact status checkpoint makes the next action understandable without a long history recap.

BEFORE / ILLUSTRATION

Done. Shall we continue?

AFTER / ILLUSTRATION

Step 2 of 3 complete: identity verified. Next: review the proposed change.

Why this rule matters

The canonical rule recommends a task or plan tool where the harness provides one. Its checklist can carry the state; do not also narrate the whole plan in prose.

Amit adaptation

Report only meaningful changes. A job marked admitted is not finished; an unchanged status does not justify a new job.

Proposed personal preference; not an upstream modification.

06
CANONICAL RULE

Give specific time estimates

Use units and state assumptions.

The source favors a concrete ballpark over phrases such as a bit of work.

BEFORE / ILLUSTRATION

This will take a while.

AFTER / ILLUSTRATION

Estimated effort: about 15 minutes if the existing tests cover the change; otherwise the estimate needs revision.

Why this rule matters

The repository example is conditional. It does not provide measured task-duration data or justify a guaranteed completion time. Its harness exception says estimates should refer to whoever will execute the steps.

Amit adaptation

No invented ETA. Prefer known progress and dependencies; provide a rough range only when its assumptions are explicit.

Proposed personal preference; not an upstream modification.

07
CANONICAL RULE

Make completed work visible

Name what now works.

State the observable outcome, rather than a vague claim that work was done.

BEFORE / ILLUSTRATION

Several improvements have been made across the implementation.

AFTER / ILLUSTRATION

The settings page now opens. The save action still needs verification.

Why this rule matters

The rule asks for concrete completed work. Keep completed and pending outcomes separate so that a visible win does not disguise a partial result.

Amit adaptation

Evidence first. Show the successful test or readback, plus the one remaining blocker when there is one.

Proposed personal preference; not an upstream modification.

08
CANONICAL RULE

Matter-of-fact tone for errors

Describe the failure without drama.

Report the observed error calmly. Separate verified causes from hypotheses.

BEFORE / ILLUSTRATION

Oh no! Authentication is definitely broken, so regenerate the token.

AFTER / ILLUSTRATION

Observed: the request returned 401. Cause: not yet verified. Next: inspect the request headers.

Why this rule matters

The source rule says to state location, cause, and fix. Its own evaluation found a case where the candidate invented a missing-auth-header cause. The evidence-first wording here is an Amit adaptation, not a silent replacement of the source.

Amit adaptation

Use observed, inferred, and unknown when needed. Concision must never manufacture confidence.

Proposed personal preference; not an upstream modification.

09
CANONICAL RULE

Cap lists to 5 items

Limit the display, not the thinking.

Group and rank long lists. Keep relevant information available rather than deleting it.

BEFORE / ILLUSTRATION

Here are eighteen equal-priority actions you could take right now.

AFTER / ILLUSTRATION

Recommended: test the smallest change. Alternative: gather the one missing diagnostic.

Why this rule matters

The canonical rule explicitly says the cap must not restrict analysis, search, tool results, candidate generation, or retained information. Completeness matters; the visible list is only a presentation choice.

Amit adaptation

Normally show at most three options and recommend one. Put the rest behind a detail control or in durable task state.

Proposed personal preference; not an upstream modification.

10
CANONICAL RULE

No preamble, no recap, no closing pleasantries

Start with the answer. Stop when done.

Remove filler that delays the useful content or repeats it at the end.

BEFORE / ILLUSTRATION

Great question. I will explain this briefly. In summary, I have now explained the concept.

AFTER / ILLUSTRATION

A workspace is a named working area. Use the verified workspace for the requested task.

Why this rule matters

This does not remove necessary context, caveats, or requested detail. Rule 5 still needs a short state cue. A useful checkpoint is different from retelling the whole conversation.

Amit adaptation

Keep a normal answer short, but preserve the full requested artifact, evidence, and any material risk.

Proposed personal preference; not an upstream modification.

Rule 1 of 10

The display limit never limits analysis or required completeness.

03 / THE ESCAPE HATCHES

The task wins. The shape stays.

These six exceptions are part of the skill, not loopholes added by this page.

01Explain fully

When the user asks for an explanation, keep the required substance and use headings. Short is not the same as incomplete.

Explain the rollout risk fully; do not compress it into an unsafe one-liner.
02Safety wins

Confirm before destructive actions. Output styling does not authorize deletion, force-push, or a production change.

Pause before a destructive migration even when the reader asks for fewer words.
03Break the debug spiral

After three still-broken turns, stop iterating on code. Name the assumption that may be wrong and ask one diagnostic question.

We changed the client three times. Are we reaching the expected server?
04Ask about real ambiguity

One short clarifying question is better than guessing and rewriting the wrong thing.

Which environment is in scope: the test environment or production?
05Keep the actual answer

When the task asks for options, give options. Do not erase them to force one next action.

Compare the requested choices, rank them, and recommend one.
06Respect the harness

Higher-priority system and harness requirements override the style. Do agent-owned work instead of asking the user to do it unnecessarily.

An approval gate remains required even when the style says action first.
Useful tension: a short state cue is helpful; a full recap is not. A calm error is helpful; a made-up root cause is not.

A 20-second pre-send review

Check the first and last lines. Can the reader locate the result and the next action? Remove an announcement that delays the answer, an empty closer, a tangent, and an idiom that hides the literal task.

Repository map ↗
What the always-on hook actually does

The inspected Node hook checks an opt-in flag in the Claude configuration directory, reads the bundled canonical skill, strips its frontmatter, and prints instructions. Without the flag it exits without injecting the rules. Errors are caught so this optional hook does not block startup.

This is a source-code description, not a live verification of every runtime. Read the matching installation section before enabling anything. The page does not create a flag, install a plugin, or modify your configuration.

Hook implementation ↗
Activation is different from installation

The canonical skill describes explicit invocation and asks the assistant to keep the style for the conversation. Saying stop adhd mode or normal mode ends that session-level instruction.

That request is not the same as removing an always-on flag or uninstalling a plugin. Use the platform-specific instructions for persistent settings. Do not assume all platforms honor the same metadata or slash commands.

The test, in plain language

14 cases × 3 trials produced 42 responses per condition.

The same model family also judged the responses, with conditions blinded. The source reports 10 case wins, 2 ties and 2 losses for the candidate.

Recorded experiment: 2 Aug 2026. Reported runner: Claude Code 2.1.220. Model label: claude-opus-4-8. Generation $2.67; judging $0.92. These are reported historical values, not a quote for your use.

Do not turn this into a personal guarantee. These are assistant-response evaluations, not a study of Amit's learning or a clinical ADHD outcome.
Limitation 1: the agent-owned edit case

That case required the agent to edit a repository, but the runner disabled tools. The source says it needs real tools with a fixture workspace, or a rewritten criterion. Otherwise it cannot test actual task execution.

Limitation 2: the partial-success regression

The candidate sometimes named a missing authorization header as a definite cause without supporting evidence. The report treats the cause-then-fix rule as a plausible mechanism, not a proven explanation. Three trials were insufficient to confirm it.

Limitation 3: limited generalization

Three trials are few, the judge used the same model family, and some responses contained tool-call syntax as plain text. Scores from this setup do not establish performance across models, runtimes or real work.

Full reported results and caveats ↗
The release rule we should preserve

The rubric requires no blocking findings, correctness and safety no more than 0.1 below baseline, and a higher weighted score. Comparisons must use matching cases, models, trials and rubric.

The existing results fail the zero-blocker condition. A higher average is not permission to hide a material failure. Fix the case design before drawing an autonomy conclusion.

07 / AMIT'S PROPOSED ADAPTATION

Extract the value.
Not another complex system.

Use the fork as a learning and experiment space. Keep the current canonical rules untouched until a change has evidence.

KEEP

Clear delivery

  • Answer or result first.
  • Small, bounded steps.
  • One concrete next action.
  • Honest visible progress.
ADAPT

Evidence before style

  • Do not invent a root cause.
  • Do not invent an ETA.
  • State only meaningful changes.
  • Keep commands opt-in.
DEFER

Global machinery

  • No immediate always-on hook.
  • No all-repository rollout.
  • No duplicated rule copies.
  • No new evaluation framework yet.
01

Try a small personal instruction

Use it for one bounded task. Change presentation only; do not widen execution, repository or financial authority.

Proposed outcome: easier to understand without losing evidence.

02

Compare against your existing KISS style

Use the same prompts and tools. Compare a status check, a partial failure, an ambiguous request, a destructive action and an agent-owned edit.

Proposed outcome: an improvement over what you already use, not just over a bare prompt.

03

Promote only the patterns that win

Keep one canonical rule set, with thin runtime adapters. Adopt only after correctness, task completion and safety hold up.

Proposal for your workflow, not a claim that Agent OS or repo-starter has been changed.

Copy the proposed Amit instruction

Personal adaptation. Copying does not install a plugin or activate anything in another application.

A small evaluation plan, not a large new project

Start with the five situations above using a fixed runtime and comparable conditions. Blind the labels when reviewing responses. Score correctness, autonomy, actionability, safety and concision using the source rubric.

Add a real temporary fixture and tools for the edit case. Do not infer autonomy from prose produced by a tool-disabled runner. Record failures and partial success explicitly. Provider-backed evaluation needs a deliberate budget; this page performs none.

Privacy, accessibility and controls

The page has no analytics, external assets, account sign-in, fetch calls or model calls. Source links leave the page only when clicked. Copy writes the selected instruction to your clipboard only after you press its button. If clipboard access is unavailable, select the text manually.

Progress is remembered in browser storage only after you opt in. Turning the option off removes this page's stored progress. Reset clears only this page's progress. There are no streaks or countdowns.

Listen uses only a browser-exposed local voice, never an automatically selected remote voice. If none is available, the control explains the limitation. Text remains fully usable. Speech availability depends on your browser and installed voices.

Use Tab to move, Enter or Space to activate buttons, and the visible Back/Next controls to navigate. Left/right arrows switch rule cards only when focus is not on a form field or control. Escape closes a pause dialog or the mobile menu. The page respects reduced-motion settings and can be printed.
